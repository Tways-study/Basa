## Pipeline

Capture → IndexedDB outbox → `POST /api/sync` → segment (Muse Spark proposes padded region boxes, one SAM 3.1 box-prompt request tightens them; both Meta API) → read each region twice (Muse Spark via Meta API; Muse Spark Open `meta-models/muse-spark-open` via Baseten) → reconcile → review UI → confirmed record and cited summary.

Model facts that shape the code (details and sources in `docs/models-notes.md`):
- SAM 3.1 uses `POST /responses` with a streamed, special-token text output (not JSON); read only the `response.output_text.delta` events. Noun-phrase prompts find only distinct objects (the stamp); box prompts segment any region and can carry all regions in one request. Parse the output into Zod-validated records in `lib/models/sam.ts`; count each SAM request against `MAX_MODEL_CALLS_PER_SCAN`. Decision 2026-10-30: boxes only. The mask byte format (base85 alphabet, layout) is not in any doc we may use, so masks are parsed but not decoded and `mask_path` stays null; the review overlay draws SAM boxes. Do not guess the mask format; add masks only when the organizers or a doc give it.
- Muse Spark uses `POST /chat/completions`, with the image as a base64 data URL, and also proposes region boxes (0-1000 grid). Reasoning counts toward `max_tokens`: send `reasoning_effort: "minimal"` with `max_tokens` 1500, and treat `finish_reason: length` or empty content as a failed reading. Use Standard-mode model IDs only, never `-contributor` (that mode lets Meta train on our content).
- Muse Spark Open on Baseten always emits `reasoning_content`. Read only `message.content`, never store the reasoning, send `reasoning_effort: "low"` with `max_tokens` 1500, and treat `finish_reason: length` as a failed reading. It cannot propose region boxes. The model is `meta-models/muse-spark-open` (no suffix) on our own Baseten account. Ruling (organizers' reply, 2026-10-31, relayed from Josh at Meta): the unsuffixed ID counts for the Open Weights requirement, using it through our own Baseten account is fine, and partner credits are not needed to compete. The `-1026` ID returned 404 for our key (checked 2026-10-29) and is not needed. Best Build on Meta Open Weight Models checks that the project runs on an eligible open-weight model. The README and demo must explain how and where Muse Spark Open is used in the workflow, and we add provenance: Baseten run logs, screen captures and outputs.

- Readers see the stored box grown by 20% of its own size (`READ_MARGIN` in `lib/pipeline/bbox.ts`, client-safe so the review screen can show the same area). A box that ends a little short of the text makes both readers drop the same words and still agree, which reconcile cannot flag. Do not remove the margin without re-measuring on `eval/fixtures/hard-chart-01.jpg`.
- Read prompts need an exact output shape. Give each region kind the JSON it must return and say any other key is wrong. A one-key schema (signature) plus the word "transcription" in the preamble made Muse Spark answer under a `transcription` key in about two runs in three (observed 2026-10-30). Keep that word out of read prompts. A reading that breaks the shared field keys is a failed reading, shown to the person, never repaired silently. An answer with no JSON in it at all is asked for once more (the retry is a real call and counts against the cap); two such answers in a row are a failed reading. Prompt tuning is logged in `docs/eval-tuning.md`: wording changes had no measurable effect, so do not add prompt sentences without a paired measurement on the dev set.
- Each stage is idempotent and persisted, so a retry never duplicates work. Stages write to the database; the UI polls job status.
- Never hold a whole scan in one request. Per-region work runs in parallel; every model call has a timeout and bounded retries. The run has one deadline (`RUN_BUDGET_MS`, 100 s, in `lib/pipeline/run.ts`) under the routes' `maxDuration` of 120 s: past it nothing new starts, in-flight calls are cut off, and every unfinished reading is stored as a failed one ("Ran out of time"), so a slow model ends in review or a clear failure, never a scan stuck on `reading` (production, 2026-11-03: model calls hung, Meta around 09:50 and Baseten around 10:10, and the 60 s limit killed the function mid-read). Each request times out after 20 s (`REQUEST_TIMEOUT_MS`; calls normally take 1 to 3 s) and is retried twice. Each reader has its own lanes, so a hung reader cannot starve the other. `maxDuration` must stay a literal in both routes; `lib/pipeline/limits.test.ts` keeps the budget, `maxDuration`, `STALE_AFTER_MS` and the page's `STALL_AFTER_MS` in order.
- Reconciliation: normalize both readings (trim, case, spacing, unit forms, numeric parsing), then compare field by field. Match = `agreed`. Different, or one unreadable = `flagged`. It is derived from the stored readings on every `GET /api/scans/[id]` (a `fields` array per region, `reconcileReadings` in `lib/pipeline/reconcile.ts`), not stored; the human decision is stored in `reviews`. A reader that failed or found nothing counts as having found nothing, so all its fields are flagged. "Agreed" means the readers matched, not that the value is right: the source crop must always be visible.
- A human confirms everything. `agreed` fields are fast-confirm; `flagged` fields require an explicit choice or edit. Never silently pick one model's answer for a flagged field.
- Review save (`POST /api/scans/[id]/review`, one region per call): the server re-derives the fields from the stored readings and `resolveReview` (`lib/pipeline/review.ts`, pure) refuses a missing field, `agreed` on a flagged field, a reader value the reader did not return, and unknown or duplicate keys. It upserts `reviews` (unique on region) and adds a `recognition_event` when the final answer changed. "Can't be read" is a stored decision (`null`, never a guess). The scan becomes `done` when every region has a stored review. The browser never writes to the database.
- Cited summary (`buildSummary` in `lib/ui/summary.ts`, `record-summary.tsx`): shown only after the record is confirmed and saved. A fixed template over the person's final answers, one line per field or table row, each citing its region ("Region 2, Table"); it never uses a reader's raw output and has no wording of its own, so it cannot add advice or inference. Hovering, focusing or tapping a line draws its region heavier on the photo (thicker border and a filled tag, not color alone).
- Read again (`POST /api/scans/[id]/resume`, `decideRetry` in `lib/pipeline/run.ts`): for a scan that `failed`, went quiet, or reached `needs_review` with a failed reading, the route puts the scan back in `reading` and runs the same pipeline, which redoes only readings that have an error. A `done` scan, one with nothing failed, and one running right now are left alone (200), so a double tap is harmless. The failure test judges every stored reading, so a retry that fails again leaves the scan in review instead of failing it. Buttons: "Read the failed ones again" on the review screen, "Try reading again" on a failed scan. A scan that shows no progress for `STALL_AFTER_MS` (160 s, `lib/ui/scan-status.ts`) also gets "Try reading again" on the results page, because a killed run leaves the status as it was. A retry gets a fresh `MAX_MODEL_CALLS_PER_SCAN`.
- Outbox: capture saves the downscaled JPEG to IndexedDB first (`lib/outbox/`), then sends through the one shared sender (`send.ts`). The photo is stored as raw bytes plus its type (`stored.ts`), never as a Blob: WebKit (every iPhone browser) will not store a Blob in a private tab, which made "saved on this device" fail on a real phone (2026-11-01); the Blob is rebuilt on read and older rows still read. No app shell is cached (no service worker, out of scope), so reopening the address while offline fails by design; the photo is safe in IndexedDB and sends when the app is next opened online. Unconfirmed review answers are kept in `localStorage` per scan (`lib/ui/review-draft.ts`) and cleared on save. The scan id is made at capture, so a repeat `POST /api/sync` is a no-op on the server. Sync runs on app start, on the `online` event, from "Sync now" and on a backoff timer; one run at a time per tab.
- Review and outbox fixes (2026-10-31, merged in PR #26, from the PR #24 review): a scan completes only when every region with fields has a stored review, and a region with no fields counts as seen only if both readers answered without error (`isScanComplete`); the source crop is no longer height-clipped; `FieldRow` no longer copies a stored decision into state once; the overlay is green only for confirmed `agreed` fields; padded reader text is compared trimmed; the `recognition_event` is written before the review and compared with the last event; Confirm names the failing region and skips regions already saved; the outbox waits for a running pass then runs its own, and its status poll handles each scan on its own. Phone runs (2026-11-01): Phases 3, 5 and 6 passed on a real phone (browser model not recorded); the real-Supabase review run was done on Oct 31. Still open: tests for the route and the two-tab outbox race. Checked at 360px on sample data (2026-10-31): no sideways scroll, every control at least 44px, no console errors, but the review screen is long (20 fields is about 7,180px, the crop shows once per region so it is off screen while answering a 12-field table, and the sticky progress bar takes about a fifth of the screen). Decision 2026-10-31 (Tways, under the scope freeze): build two small changes, flagged-first ordering (regions and fields that need a person come first, except that header regions always stay on top, `reviewOrder` in `review-state.ts`, issue #49; region numbers stay in reading order because the photo marks use them; the order depends on reader status only, never on the person's answers, so a field does not jump while it is answered) and a printed patient copy (`record-print.tsx`, below). Collapsing agreed fields is not done: it would hide values before a bulk confirm, against "show the source beside every value". The real-phone steps for Phases 3, 5 and 6 are in the phone test sheet (artifact `RXnzr3KLyETQAWQwKKSmXF`).

## Stack

Next.js (App Router), TypeScript strict, Tailwind, shadcn/ui (Radix primitives, restyled to our palette), lucide-react (icons), GSAP with `@gsap/react` (SAM mask reveal only), Supabase (Postgres and Storage, RLS on every table), Zod on every external input and every model output, IndexedDB via `idb`, Vitest (unit), Playwright (one happy-path e2e), Vercel. Package manager: pnpm. Prefer Server Components; use `"use client"` only for capture, the outbox, and the screens that poll or review (results page, review screen).

Next.js 16 with `cacheComponents`: anything that reads `params`, `searchParams` or other request data must sit inside `<Suspense>`. This version differs from older Next.js examples, so read the matching guide in `node_modules/next/dist/docs/` before using a Next.js API.

## Shared field keys

The contract between model output, reconcile, the review screen, and the ground-truth files. Change it only when all three of us agree.

| Region | Keys |
|---|---|
| table | `row{n}.test`, `row{n}.value`, `row{n}.unit` |
| handwriting | `line{n}` |
| stamp | `stamp.present`, `stamp.text` |
| signature | `signature.present` |
| header | `header.patient_name`, `header.chart_no`, `header.date` |

`n` counts from 1, top to bottom. Unclear text is `null`, never a guess. A row only one reader found is `flagged` automatically.

## Design direction

Paper-and-ink editorial, built for tired eyes in a bright clinic. Not a generic SaaS dashboard.

- Fonts: Fraunces (display), IBM Plex Sans (body), IBM Plex Mono (extracted values). Never Inter, Roboto, Arial, or system-ui as primary.
- Colors as CSS variables: paper `#F4EFE6`, ink `#1B1A17`, muted line `#D9D2C3`, verified green `#2F6B4F`, flag amber `#B7791F`, stamp red `#C8341F`. Color carries meaning only: green = models agreed, amber = needs a human, red = unreadable or failed.
- The review screen is the hero: source crop and both readings side by side, flagged fields impossible to miss, touch targets of at least 44px, works from 360px wide up to desktop.
- Motion only where it explains something: SAM masks animating in, status badge changes. Respect `prefers-reduced-motion`.
- shadcn: use only the components we need, mapped to the palette variables and Fraunces / IBM Plex. No default shadcn theme, no Inter. Keep the six palette variables in `app/globals.css` when running `shadcn init`.
- Amber `#B7791F` on paper is only about 3.2:1, below AA for text, so use amber as a fill or border with ink text, never as small text. Green (about 5.5:1) and red (about 4.6:1) pass.
- One 6px radius everywhere. Buttons and badges use the variants in `components/ui/`; targets are at least 44px tall (56px for the main capture action).
- Icons come from lucide-react only. Decorative icons get `aria-hidden`; an icon-only control gets an `aria-label`. Pair color with an icon or text (agreed = Check, flagged = TriangleAlert, unreadable = CircleX) so meaning never rests on color alone.
- GSAP is only for the SAM overlay reveal on the review screen (SAM boxes until masks are decodable): a lazy-loaded client component, `useGSAP`, and `gsap.matchMedia()` for reduced motion. Never in capture or the outbox. Status badges use CSS transitions.
- Accessibility: AA contrast, keyboard-operable review, a label on every control. The word Basa is Filipino for "read"; wherever the copy explains it, mark the word `lang="fil"` so a screen reader says it correctly (see the capture screen).
